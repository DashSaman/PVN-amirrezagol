# EtherIP — Data Path and Wire Flow

Review date: 2026-08-14 UTC

## RFC flow

`Ethernet / IEEE 802.3 frame (without FCS)`
→ `16-bit EtherIP header (version 3, reserved=0)`
→ `IP packet with protocol=97`
→ routed IP network
→ peer validates EtherIP header
→ recovered Ethernet frame
→ local L2 forwarding/bridge (FCS regenerated by local link layer as applicable).

RFC 3378 requires invalid version/reserved values to be discarded and warns about loop/security implications.

## SoftEther reviewed path

Pinned `Proto_EtherIP.c` evidence:

- `SearchEtherIPId(...)` resolves mapping (including wildcard behavior);
- mapping supplies Hub/User/Password to `NewIPC(..., IPC_LAYER_2)`;
- receive path validates EtherIP header and forwards recovered frames through `IPCSendL2(...)`;
- return path receives Virtual-Hub frames with `IPCRecvL2(...)`, prepends EtherIP header and transmits;
- mapping-version changes can trigger reconnect;
- EtherIP remains distinct from the same source file's L2TPv3 mode.

No runtime packet receipt is claimed by this document.
